# Rust against Neo4j in the strain benchmark

Computed from the site's published strain evidence: 32 verified publications, 2026-09-05 to 2026-09-16, 331 runs, 1,097 current cells (805 superseded cells are excluded). Generated by `scripts/render-rust-vs-neo4j.py` with the strain page's own functions (`scripts/render-strain-summary.py`), so the two agree.

## The short answer

Across 166 same-machine pairs, 6 of the 8 Rust backends with pairs beat Neo4j · Bolt in every pair on at least one metric; Neo4j · Bolt reaches the largest whole graph clean on all four core families (com-Orkut, 117.2 M edges), and Turso · WAL matches it.

- **Turso · WAL** is faster than Neo4j · Bolt every time at: loading (6/6, median 1.5× faster); hub fan-out (6/6, median 6.5× faster); deep walk (6/6, median 7.6× faster); cold start (3/3, median 2.0× faster); p99 at 200 req/s (4/4, median 4.0× faster).
- **Turso · MVCC** is faster than Neo4j · Bolt every time at: hub fan-out (7/7, median 3.8× faster); deep walk (7/7, median 3.9× faster).
- **grust-memory** is faster than Neo4j · Bolt every time at: loading (5/5, median 15.8× faster); hub fan-out (5/5, median 104.7× faster); 100 hot-node writes (5/5, median 137.2× faster); cold start (3/3, median 16.2× faster); p99 at 200 req/s (3/3, median 5.7× faster).
- **SurrealDB · HTTP** is faster than Neo4j · Bolt every time at: 100 hot-node writes (2/2, median 2.7× faster).
- **SurrealDB · SDK** is faster than Neo4j · Bolt every time at: 100 hot-node writes (2/2, median 2.1× faster).
- **HelixDB · SDK** is faster than Neo4j · Bolt every time at: hub fan-out (2/2, median 1.7× faster).
- **LanceDB** beats Neo4j · Bolt in every pair on none of its 6 paired metrics; it is slower in every pair on 5 of them.
- **HelixDB · HTTP** beats Neo4j · Bolt in every pair on none of its 6 paired metrics; it is slower in every pair on 6 of them.
- **Reach.** Neo4j · Bolt is clean, all four core families (A1, A2, A4, A12) passing, on every whole untyped graph up to com-Orkut (117.2 M edges).
- **Turso · WAL** is clean up to com-Orkut (117.2 M).
- **Turso · MVCC** is clean up to com-Orkut (117.2 M).
- **grust-memory** is clean up to soc-Pokec-relationships (30.6 M); it also loads com-Orkut (117.2 M) and passes every family it ran there, but not all four ran, so that graph does not count as clean.
- **LanceDB** is clean up to cit-Patents (16.5 M).
- **The Rust servers** (SurrealDB · HTTP, SurrealDB · SDK, HelixDB · HTTP, HelixDB · SDK) have pairs only on email-Eu-core, ego-Facebook, because they do not load larger graphs under the standard envelope; each is clean up to 88.2 k edges.

## How the comparison was made

- **A pair** is one Rust backend and Neo4j · Bolt that both **passed** the same scenario on the same graph, the same edge slice and the same machine (the same host and CPU count), under the standard configuration (6 GiB containers, each store's defaults). Rows from different machines are never compared.
- **Faster** compares the metric below; the ratio is Neo4j's value over the Rust store's, so above 1 means the Rust store was faster.
- **Always faster** means the Rust store won every pair, with at least two pairs; **never faster** means it won none, with at least two.
- **Metrics:** loading (wall time to load the graph), A1 hub fan-out (k-hop layers from the highest-degree vertex), A2 deep walk (hop-by-hop reach on a high-diameter graph), A4 (a hundred concurrent writers attaching edges to one hub), A12 cold start (fresh handle to first correct answer) and A12 p99 response time of an open-loop read stream at 200 requests per second.
- **Not compared:** memory footprint. A server reports its container's memory; an embedded store's only figure is the whole harness process, reference graph included, so the two are not the same measurement.

## Caveats

- **In process against over the network.** grust-memory, Turso and LanceDB answer inside the harness process with no network hop and no serialization. Neo4j answers over Bolt from a container. Part of every in-process difference is that architecture, not the language.
- **Embedded stores are not in the 6 GiB container.** They are bounded by the host's memory guard, so a reach comparison between an embedded store and a containerized server is not memory for memory.
- **Different access paths.** The Rust stores are driven through Grust adapters; Neo4j through the harness's own Cypher over Bolt.
- **Few pairs for the servers.** SurrealDB and HelixDB are comparable only on the smallest graphs.
- **A4 is not the same work everywhere.** Turso's WAL journal refuses most concurrent writes with typed conflicts by design, so its A4 time covers fewer applied writes than Neo4j's; Turso's MVCC journal accepts them all.
- **Profiles.** Pairs use each store's harness-default profile only. Turso MVCC rows taken at `synchronous = NORMAL` are not default and are not paired, so every hot-node-write pair compares durable commits on both sides.
- **One current cell per graph and store.** The page keeps the newest default-profile run of each cell regardless of machine, so a pair exists only where both stores' current cells are on the same machine; pairs from earlier runs on other machines are in the page's history, not here.
